# Changelog — Clear GPS

Этот файл — постоянный журнал изменений проекта, прежде всего ветки `dev`. Он нужен, чтобы понять не только **что изменилось**, но и **зачем, где и с какими последствиями**.

## Как вести этот журнал — обязательно для каждой следующей работы

При каждом изменении кода, спецификации, сборки, CI или структуры проекта в ветке `dev` обновляй этот файл в том же коммите, что и само изменение.

Для каждой записи указывай:

1. **Дата и коммит** — дата изменения и ссылка на коммит, если он уже создан.
2. **Зачем** — проблема или цель по плану проекта. Не писать только «рефакторинг» без объяснения причины.
3. **Что изменено** — точные пути файлов и краткое описание роли каждого изменения.
4. **Поведение и последствия** — что изменится для приложения, сборки, данных, приватности или совместимости; отдельно отмечай, если пользовательское поведение не менялось.
5. **Проверки** — конкретные тесты/команды и их результат. Не объявлять сборку успешной, пока результат действительно не получен.
6. **Ограничения и дальнейшие шаги** — нерешённые вопросы, если они остались. Не выдавать планируемую работу за завершённую.

Правила:
- Пиши так, чтобы через несколько месяцев другой разработчик мог понять мотив и последствия, не восстанавливая весь разговор.
- Добавляй новые записи сверху, ниже инструкций, сохраняя историю старых изменений. Не переписывай старые записи так, чтобы терялась история.
- Группируй связанные файлы по одной задаче; перечисляй все затронутые пути.
- Если поведение намеренно не менялось, укажи это.
- Если тесты не запускались или результат неизвестен, укажи это прямо.
- Не добавляй функции и требования, которых нет в утверждённом плане или прямом поручении.
- Для каждого последующего изменения в `dev` обновление журнала — часть готовой работы, а не необязательное оформление.

### 2. Выделен модуль GNSS-детектора

**Коммит:** [3ca0621](https://github.com/MAKAKAIglitch/clear-gps/commit/3ca062120ecc683decd6cf41ab0f96ccc4aa1b5e)

**Зачем:** начать отделять платформонезависимое ядро от Android-слоя, чтобы алгоритм можно было проверять обычными unit-тестами и в дальнейшем развивать независимо от интерфейса и системных сервисов.

**Изменённые файлы:**

- `core-detect/build.gradle.kts` — добавляет отдельный Kotlin/JVM-модуль и его тестовую зависимость JUnit.
- `core-detect/src/main/kotlin/org/cleargps/core/GnssSpoofingDetector.kt` — перенесён существующий детектор GNSS и его типы входных данных/оценки.
- `core-detect/src/test/kotlin/org/cleargps/core/GnssSpoofingDetectorTest.kt` — перенесены существующие unit-тесты детектора.
- `settings.gradle.kts` — зарегистрирован модуль `:core-detect`.
- `build.gradle.kts` — зарегистрирован Kotlin/JVM Gradle-плагин.
- `app/build.gradle.kts` — Android-приложение подключает `:core-detect`.
- `.github/workflows/android.yml` — CI запускает тесты нового модуля перед Android-тестами и сборкой.
- `windows-build/build-apk.ps1` — Windows-сценарий сборки также запускает тесты `:core-detect:test` перед существующими проверками и сборкой.

**Что принципиально не менялось:** алгоритм детектора не переписывался при переносе. Цель коммита — выделение границы модуля, а не улучшение точности детектирования. Остальные Android-модули пока не вынесены.

**Проверки:** GitHub Actions завершил запуск [40234532526](https://github.com/MAKAKAIglitch/clear-gps/actions/runs/40234532526) со статусом `success` для этого коммита — тесты/сборка и Windows smoke-test прошли в CI.

## 2026-10-26 — Усилены проверки политики mock-публикации

**Задача:** сделать один из первых этапов дорожной карты безопаснее — зафиксировать тестами, какие Android-провайдеры допустимо заменять в GPS/Auto и Radio режимах, и проверить валидацию координат перед публикацией.

**Изменённые файлы:**

- `app/src/main/java/org/cleargps/MockLocationOutput.kt` — проверка широты/долготы вынесена в небольшую чистую функцию `isValidMockCoordinate`. Логика проверки не изменилась: координаты должны быть конечными и находиться в допустимых диапазонах WGS84.
- `app/src/test/java/org/cleargps/MockLocationOutputPolicyTest.kt` — вместо нескольких точечных проверок добавлена матрица API 26, 30, 31 и 35 для политики провайдеров; добавлены проверки, что GPS/Auto не выбирают GPS/network test-provider, что Radio выбирает их только при разрешении политикой, и что некорректные/нечисловые координаты отклоняются.

**Зачем:** исключить регрессию, при которой GPS/Auto могут заменить собственный физический GPS/network-вход, и зафиксировать граничные случаи валидации позиции перед передачей в Android.

**Поведение приложения:** алгоритм детектора и маршрутизация публикации не менялись; это выделение уже существующей проверки и расширение unit-тестов.

**Проверки:** GitHub Actions run [40235077097](https://github.com/MAKAKAIglitch/clear-gps/actions/runs/40235077097) завершился успешно для коммита с этими тестами. Unit-тесты проверяют чистую политику выбора провайдеров, но сами по себе не заменяют инструментальную проверку на реальном Android-устройстве; реальная доставка координат сторонним приложениям остаётся отдельным пунктом дорожной карты.

**Ограничения:** публикация во всех режимах ещё не подтверждена инструментальным тестом на реальном Android-устройстве.


## 2026-10-26 — Сигнальные предупреждения учитывают непрерывность измерений

**Задача:** уменьшить ложные предупреждения при редких GNSS callback-ах или после длительной потери измерений. Признак «сильные сигналы, но мало спутников участвует в фиксе» должен подтверждаться несколькими близкими по времени снимками, а не отдельными наблюдениями, разделёнными длительной паузой.

**Изменённые файлы:**

- `core-detect/src/main/kotlin/org/cleargps/core/GnssSpoofingDetector.kt` — серия наблюдений с сильными сигналами учитывается как последовательная только при интервале 0,2–12 секунд; после длинной паузы текущий снимок начинает новую серию. Ранее проверка резких изменений уже использовала это временное окно, но счётчик «сильный сигнал / мало спутников в фиксе» мог накапливаться через длинный разрыв.
- `core-detect/src/test/kotlin/org/cleargps/core/GnssSpoofingDetectorTest.kt` — добавлен регрессионный тест: два подозрительных наблюдения, разделённые паузой 28 секунд, не должны давать предупреждение; два последующих последовательных наблюдения по-прежнему могут дать предупреждение, но не подтверждают атаку.

**Зачем:** потеря/редкость измерений и контекст плохого приёма не должны сами по себе превращаться в усиленное подтверждение спуфинга. Это реализует требование плана учитывать давность и последовательность сигналов.

**Поведение:** меняется только подсчёт одного сигнального признака. Другие проверки, пороги и расчёт позиции не менялись. Индекс остаётся уровнем риска, а не вероятностью.

**Проверки:** новый unit-тест добавлен в модуль `:core-detect`. GitHub Actions run [40235236641](https://github.com/MAKAKAIglitch/clear-gps/actions/runs/40235236641) завершился успешно: модульные тесты, Android-тесты/сборка и Windows smoke-test прошли.


## 2026-10-26 — Сигнал о внешней mock-геопозиции

**Задача:** реализовать пункт плана о выявлении mock-координат от другого приложения, когда собственная mock-публикация Clear GPS выключена.

**Изменённые файлы:**

- `app/src/main/java/org/cleargps/ExternalMockLocationPolicy.kt` — добавлена чистая политика: сигнал относится к внешнему mock только для GPS/network provider, если координата помечена Android как mock и собственная mock-публикация выключена.
- `app/src/main/java/org/cleargps/LocationMonitorService.kt` — mock-callback больше не игнорируется одинаково во всех случаях. При выключенном собственном mock и mock-callback от GPS/network приложение формирует сильное предупреждение, не использует координату для фильтра или публикации, очищает собственную устаревшую mock-публикацию и показывает уведомление. Когда собственный mock включён, ожидаемые mock-callback-и по-прежнему игнорируются.
- `app/src/test/java/org/cleargps/ExternalMockLocationPolicyTest.kt` — добавлены тесты для GPS, network, не-mock координат, включённого собственного mock и неотслеживаемых провайдеров.

**Зачем:** это закрывает явно указанный в плане случай «чужой mock» и не позволяет принять отмеченную Android mock-координату за физическое GNSS-измерение.

**Поведение и ограничения:** сигнал создаётся только при получении callback-а от наблюдаемого GPS/network provider. Это не доказывает вредоносность приложения-источника и не гарантирует обнаружение mock-данных, скрытых/перепакованных провайдерами Android. Сигнал не активируется, пока включён собственный mock Clear GPS, согласно принятому плану. Очистка собственного mock-провайдера вызывается только если сохранённое состояние говорит, что публикация ещё активна, чтобы повторные внешние callback-и не приводили к лишнему снятию провайдеров и диагностическому шуму.

**Проверки:** добавлены unit-тесты политики классификации; CI для этого коммита ещё должен подтвердить успешную сборку и тесты. Инструментальная проверка внешнего mock на реальном Android-устройстве всё ещё необходима.
