## 1. Что означает визуальное направление

GrapheneOS не задаёт отдельный «пиксельный» дизайн-системный язык для сторонних приложений. Проект основан преимущественно на Android Open Source Project и использует собственные изменения поверх AOSP. Поэтому корректнее ориентироваться на спокойную системную эстетику Android Settings / Material You: типографическая иерархия, нейтральные поверхности, крупные зоны нажатия, простые строки параметров, системные переключатели и ненавязчивые переходы.

Источник: https://grapheneos.org/source

- Сохранить текущую палитру Material 3 и dynamic color, чтобы интерфейс естественно адаптировался к системной теме устройства.
- Использовать более просторную сетку: горизонтальные поля 20 dp, вертикальный ритм 14 dp.
- Применить более мягкие системные формы поверхностей с радиусами 22–24 dp и низкоконтрастными surfaceContainer оттенками.
- Повысить визуальную иерархию заголовка экрана без декоративной графики.
- Сделать всю строку настройки нажимаемой, а не только маленький переключатель; оставить стандартный Material Switch как индикатор состояния.
- Раскрывать и сворачивать большие группы через `AnimatedVisibility` с fade + expand/shrink от верхнего края; анимировать стрелку раскрытия.
- Не менять названия параметров, значения, callbacks, условия согласия, сетевые разрешения, лимиты, источники данных и поведение фоновой службы.

## 7. Поиск настроек и упорядочивание экрана

Продолжение работы от 27-11-2026.

### UX-решения

- Поиск вынесен сразу под заголовок настроек; строка остаётся доступной независимо от раскрытия групп.
- Индекс включает 33 поисковых пункта с русскими/английскими синонимами: например, Bluetooth ↔ BLE, Wi-Fi ↔ вайфай, батарея ↔ энергосбережение, GNSS ↔ спутники.
- Запрос разбивается на слова; каждое слово должно находиться в названии или словаре синонимов пункта. Это позволяет искать сочетания вроде «wifi батарея», а не только одну непрерывную фразу.
- Результаты появляются в отдельной тональной поверхности. Изменение набора результатов использует Crossfade; появление панели, скрытие основного списка и очистка поля анимируются.
- Нажатие на результат открывает нужную группу и плавно прокручивает экран к ней.
- Режим положения теперь расположен первым как основная настройка. Сетевые согласия и внешние источники собраны в отдельную сворачиваемую группу «Сеть и приватность», закрытую по умолчанию. Это сокращает начальную высоту экрана и оставляет основные параметры на первом плане.

## 8. Исправление падения Android CI: устаревшие ожидания версии БД

Проверка workflow `45900636646` выявила одинаковое падение на Linux и Windows: 582 теста запускались, но два migration-теста завершались `AssertionError`:
- `v19UpgradeAddsCompactMacIndexWithoutChangingStoredObservations` — ожидал `SQLiteDatabase.version == 20`.
- `v4DatabaseMigrationPreservesRowsAndAttributesLegacyWigleProvenance` — также ожидал версию 20.

В актуальной схеме `LocalRadioDatabase` версия уже 21. В `onUpgrade()` миграция для `oldVersion < 20` создаёт компактный MAC-индекс, а следующая миграция для `oldVersion < 21` добавляет поддержку ускорения fingerprint-запросов. Поэтому старые версии 19 и 4 корректно обновляются до 21; production-миграция не была причиной сбоя. Ошибка находилась в двух устаревших ожиданиях тестов.

Исправление в коммите `b8937ba760ee1cb33a4946d90090242f1b539b8f`: оба ожидания заменены на 21. Проверки данных, индексов и происхождения WiGLE оставлены без ослабления. Следующий шаг — подтвердить зелёный Linux/Windows CI на новом коммите.

## 9. Диагностика подписи APK и стабильная подпись GitHub Actions

Дата: 27-11-2026. Область: причина отказа Android при обновлении установленного debug-приложения.

### Факты с устройства

- Установленный пакет: `org.cleargps.debug`, версия `0.4.0-debug`, versionCode `4`.
- Сертификат установленного APK: SHA-256 `b9d0a44493f14d48c52e37703daee00f88320e507d84e513c0790c0b37f06d8c`.
- Сертификат скачанного `app-debug.apk`: SHA-256 `920fd61fa844346d087b8085836c06f517568a29c84000466c78ac045f49708e`.
- Отпечатки различаются; Package Manager вернул `INSTALL_FAILED_UPDATE_INCOMPATIBLE` с сообщением о несовпадении подписей. Следовательно, причина отказа подтверждена.

### Проверка конфигурации репозитория

Ветка `dev`, файлы `.github/workflows/android.yml`, `.github/workflows/android-build.yml` и `app/build.gradle.kts` проверены.

- Workflow собирает `assembleDebug` на GitHub-hosted Linux и Windows runners.
- В Gradle явно не задан постоянный `signingConfig` для debug; применяется стандартная debug-подпись Android Gradle Plugin.
- GitHub-hosted runner — эфемерная среда. Debug keystore, автоматически созданный на таком runner, не является гарантированно постоянным между запусками и платформами. Поэтому APK из разных CI-запусков может иметь разные сертификаты.
- Workflow загружает debug APK как artifact; release signing и публикация Release в этих workflow не настроены.

### Вывод и безопасный план

Да, keystore можно хранить в GitHub Actions Secrets (например, base64-значение keystore и отдельные пароли/alias), а workflow может восстановить его во временный файл и настроить Gradle signing для всех последующих сборок. Но это поможет обновлять уже установленную копию только если имеется исходный keystore, соответствующий её сертификату.

Сертификат/публичный SHA-256 из APK не содержит закрытого ключа и не позволяет восстановить keystore. Если исходный keystore, которым подписан установленный APK, не сохранился, просто добавление нового keystore в Secrets не позволит обновить текущую установку поверх неё. Сначала нужно найти исходный keystore или отдельно спланировать контролируемую миграцию установки и данных. Не предлагать удаление приложения или очистку данных как первый шаг.

Никакие секреты или приватные пользовательские данные в этот research-файл не добавлялись.

## 11. Диагностика чёрной карты: неполный allowlist ресурсов OpenFreeMap

Дата: 27-11-2026. Область: загрузка базовой карты MapLibre.

### Подтверждённая причина в коде

NetworkGate.validateRequest() разрешал для tiles.openfreemap.org только пути /styles/, /data/, /fonts/ и /assets/. Но актуальные live-стили OpenFreeMap Liberty и Dark используют дополнительные ресурсы на том же хосте:
- векторный TileJSON: /backup_planet, который возвращает шаблон тайлов /backup_planet/20261122_124456_pt/{z}/{x}/{y}.pbf;
- растровые тайлы Natural Earth: /natural_earth/ne2sr/{z}/{x}/{y}.png;
- спрайты: /sprites/ofm_f384/ofm.json и соответствующие изображения;
- шрифты: /fonts/{fontstack}/{range}.pbf.

Так как NetworkGate.installMapLibre() проверяет каждый сетевой exchange через interceptor, эти запросы отклонялись политикой приложения. Стиль мог загрузиться, но базовые векторные/растровые данные и спрайты — нет; это согласуется с симптомом пустой/чёрной карты.

Проверка выполнена по текущим JSON-стилям:
- https://tiles.openfreemap.org/styles/liberty
- https://tiles.openfreemap.org/styles/dark
- https://tiles.openfreemap.org/backup_planet

### Исправление в ветке dev

- В allowlist добавлены только конкретные семейства ресурсов OpenFreeMap: точный /backup_planet и /backup_planet/…, /natural_earth/…, /sprites/….
- Сохранены ограничения: только HTTPS, точный хост tiles.openfreemap.org, GET, порт 443 или стандартный, и только при включённом online-режиме.
- Добавлены unit-тесты для URL ресурсов Liberty/Dark и тест отказа для постороннего пути.
- Код не расширяет доступ к другим хостам и не разрешает произвольные методы.

Коммиты:
- 9884df92ce23144aa1601449c1165489ce479561 — исправление allowlist.
- 4fa6bf7084b502ab8e527e7814b57160dc938a85 — тесты ресурсов OpenFreeMap.

### Проверка

После коммитов требуется Android CI: NetworkGateTest и полная сборка. Затем визуальная проверка APK на устройстве в online-режиме, в светлой и тёмной темах. Локальный запуск приложения на устройстве в рамках этого исследования не выполнялся.

## 13. Исправление пропадающих Wi-Fi/сотовых точек при ограничении карты и пояснение радиопогрешности

Дата: 27-11-2026. Ветка: `dev`.

### Причина исчезновения типов точек

Проверены `ClearGpsMapController.updateRadioPoints()`, `renderRadioPoints()`, `WifiNetworkGroupingPolicy.buildMapMarkers()`, `RadioMapPointLimitPolicy` и `LocalRadioDatabase.listMapPoints()`.

- MapLibre уже кластеризует Wi-Fi, cell и BLE по отдельным GeoJSON-источникам (`withCluster(true)`, радиус 48 px, cluster max zoom 14).
- Для каждого типа уже существуют отдельные круговые слои кластеров и подписи `point_count_abbreviated`; нажатие на кластер приближает карту к его центру.
- Реальная проблема была до MapLibre: SQLite загружала все геолокированные записи единым запросом `ORDER BY last_seen DESC LIMIT ?`. Поэтому свежие BLE-наблюдения могли заполнить лимит карты (по умолчанию 50 000 строк) и вытеснить более старые Wi-Fi/cell записи. Кластеризатор не может показать точки, которые не были загружены.

### Исправление

- `RadioMapPointLimitPolicy.allocatePerTypeLimits()` распределяет общий лимит между wifi/cell/ble с минимальной квотой для каждого присутствующего типа и пропорциональным распределением оставшегося бюджета по числу доступных строк.
- `LocalRadioDatabase.listMapPoints()` теперь получает число координатированных строк каждого типа, выбирает записи каждого типа в пределах его квоты, затем объединяет и сортирует их по свежести. Параметры SQL остаются bind-параметрами.
- Добавлены тесты на случай, когда BLE значительно многочисленнее Wi-Fi/cell, загрузку всех строк при небольшом объёме базы и соблюдение общего лимита.
- Существующая MapLibre-кластеризация сохраняется: при отдалении точки каждого типа собираются в кластеры с количеством, при нажатии карта раскрывает кластер приближением. Это не меняет исходные записи базы.

### Радиопогрешность

В текущем fingerprint-алгоритме число порядка сотен метров может быть намеренно увеличено, если одинаково похожие исторические радиоснимки найдены в удалённых местах. Также учитываются разброс кандидатов, точность исходных фиксов, число совпавших сигналов и score совпадения. Простое уменьшение числа без новых доказательств сделало бы оценку более красивой, но менее честной.

- В `RadioEstimate` добавлен флаг `ambiguousFingerprint`, чтобы UI мог отличать неоднозначность исторической базы от обычного радиосовпадения.
- Для режима радио подпись теперь говорит «Радиооценка: неопределённость около ±N м», а не называет это GPS-точностью.
- При неоднозначных снимках UI объясняет, что выбран лучший кандидат, а радиус увеличен из-за совпадений в разных местах.
- Числовая модель погрешности не занижалась искусственно. Для её калибровки нужны проверочные замеры с известными координатами.

## 12. Аудит использования RSSI/RSRP в локальном радиопозиционировании

Дата: 27-11-2026. Ветка: dev. Область: локальный поиск координат по SQLite, историческим fingerprints и радиоточкам. Личные данные не включены.

### Подтверждённые факты по исходникам

1. Основной путь локального позиционирования — `LocalRadioDatabase.evaluatePosition()`:
   - сначала загружает исторические сканы через `loadFingerprintSamples()`;
   - затем сравнивает их в `lookupRadioFingerprintPosition()`;
   - только если fingerprint не дал оценки, использует `estimateRadioAnchorPosition()` по координатам отдельных радиоточек.

2. Fingerprint использует RSSI, но его влияние ограничено:
   - сходство уровня сигнала вычисляется как `exp(-abs(current.rssi - old.rssi) / 18)`;
   - итоговый коэффициент внутри типа радио: `0.55 + 0.45 * rssiSimilarity`;
   - следовательно, даже очень плохое совпадение уровней оставляет базовые 55% оценки сходства. Совпадение идентификаторов и покрытие набора часто доминируют над реальной разницей уровней сигнала.
   - При выборе координаты исторического скана итоговый вес зависит от `candidate.score^4`, свежести и accuracy исторического reference-fix.

3. Резервная оценка по точкам использует RSSI:
   - `rssiFactor = exp((signal.rssi + 70) / 35)`, с ограничением 0.55..1.8;
   - дополнительно применяются точность и возраст точки, тип радио, доверие источника;
   - затем суммарные веса нормализуются с лимитами по типам радио. Это ослабляет влияние одного типа при большом количестве его точек.
   - Внутри комментария алгоритм прямо описан как conservative fallback, где RSSI лишь слегка сдвигает вес, а не трактуется как расстояние.

4. LTE/NR имеют потерю доступной информации в основном positioning-пути:
   - `parseCell()` передаёт `CellSignalStrength.dbm` в общее поле `RadioSignal.rssi`;
   - одновременно LTE `rsrpDbm` и NR `ssRsrp`, а также RSRQ/SINR сохраняются в `CellSignalMetadata`;
   - `recordScan()` записывает `RadioSignal.rssi` в `radio_observations.rssi`;
   - fingerprint SQL загружает `radio_observations.rssi` и не присоединяет таблицу `cell_observation_details` для RSRP/RSRQ/SINR.
   - Поэтому LTE/NR quality metadata существует в БД, но не участвует в основном fingerprint scoring как самостоятельный сигнал. Для cell-anchor fallback также используется общее поле RSSI из точки.

5. Wi-Fi использует Android `ScanResult.level` в dBm, BLE использует RSSI из BLE scan result. Для Wi-Fi/BLE текущий RSSI сравнивается с историческим полем `radio_observations.rssi`.

### Вывод

Ощущение, что RSSI почти не влияет на результат, имеет техническое основание: fingerprint придаёт RSSI максимум 45% влияния внутри типа радио, а fallback ограничивает RSSI-множитель. Дополнительно LTE/NR RSRP хранится отдельно и не входит в fingerprint SQL. Это подтверждённый недостаток использования измерений, но не доказательство того, что все оценки ошибочны: реальная ценность RSSI зависит от стабильности среды и качества reference-координат.

### Рекомендуемое направление исправления (ещё не реализовано)

- Разделить радиометрики по технологии: Wi-Fi RSSI; BLE RSSI; GSM RSSI; WCDMA RSCP; LTE RSRP/RSRQ; NR SS-RSRP/SS-RSRQ/SS-SINR. Не смешивать их как будто это одна и та же измерительная шкала.
- Добавить в исторический fingerprint scoring использование подходящей метрики по технологии, сохранив fallback на legacy `rssi` для старых строк и импортов.
- Учитывать как абсолютную разницу dB, так и относительный профиль уровней среди совпавших сигналов; ограничивать влияние выбросов и не позволять одному очень сильному сигналу подавлять остальные.
- Считать качество evidence отдельно от числа совпавших идентификаторов: показывать число сравнённых метрик, среднюю/медианную разницу dB, покрытие набора, возраст истории и разброс reference-координат.
- Для fallback по радиоточкам расширить/калибровать влияние RSSI только после тестов на наборах с известными координатами; не переводить RSSI в расстояние без локально откалиброванной модели.
- Добавить regression tests на выбор fingerprint-кандидата при конфликте покрытия и RSSI, на legacy rows без RSRP и на LTE/NR, где RSRP отличается от общего dbm.
- Отдельно проверить, что оценка accuracy учитывает слабое совпадение RSSI и неоднозначные удалённые fingerprints, а не только число совпадений и accuracy исторического фикса.

### Источники

- Исходники `LocalRadioDatabase.kt`, `RadioGeolocationRepository.kt` и `LocalSignalPositionTest.kt` в ветке dev.
- Исследования по crowdsourced cellular localization и hybrid TA/RSRP: https://www.mdpi.com/2079-9292/14/12/793
- Обзор cellular localization / fingerprinting: https://link.springer.com/article/10.1186/s13638-019-1459-4
- Android cell signal metrics are technology-specific; implementation stores RSRP/RSRQ/SINR in `CellSignalMetadata`, while legacy generic `rssi` remains the main scan value.

Статус: аудит выполнен; алгоритм пока не изменён. Перед реализацией требуется согласовать миграцию хранения исторических LTE/NR метрик и регрессионные тесты, чтобы не испортить старые базы.


## 13. Частота Wi-Fi сканирования и задержка получения результатов

Дата: 27-11-2026. Ветка: dev. Область: `WifiManager.startScan()` в `RadioGeolocationRepository.collectWifi()`. Личные данные не включены.

### Подтверждено в коде Clear GPS

- `RadioFixReliability.WIFI_MIN_REQUEST_INTERVAL_MS = 30_000L`: приложение само ограничивает новые запросы одним разом в 30 секунд.
- Это не случайный большой интервал: он точно соответствует системному пределу Android 9+ для foreground-приложения — до четырёх запросов за две минуты.
- В фоне Android ограничивает все фоновые приложения совместно до одного Wi-Fi scan за 30 минут. Поэтому foreground service не гарантирует, что система считает запросы foreground-сканированием; важен фактический process state/режим ОС.
- `collectWifi()` вызывает `startScan()`, затем при принятом запросе опрашивает `getScanResults()` каждые 250 мс до 3 секунд, ожидая timestamp новее времени запроса.
- Если запрос отклонён или сработал 30-секундный cooldown, код читает системный кэш; результаты фильтруются по возрасту до 45 секунд.
- `startScan()` может вернуть false при throttling, выключенном устройстве/сканировании или ошибке Wi-Fi HAL. Сам факт вызова не означает, что новое сканирование выполнено.
- `collectSnapshot()` запускает Wi-Fi, BLE и cell сбор параллельно, поэтому Wi-Fi polling может добавлять до 3 секунд к сбору snapshot только когда новый запрос принят и caller ожидает свежий результат.

### Android platform behavior (официальная документация)

- Android 9 и Android 10+: foreground app — максимум 4 scan requests за 2 минуты; фоновые приложения совместно — 1 scan за 30 минут.
- На Android 10+ broadcast `SCAN_RESULTS_AVAILABLE_ACTION` рассылается также после полных Wi-Fi сканирований, инициированных системой или другими приложениями. Приложение может пассивно слушать результаты без собственного `startScan()`.
- `getScanResults()` возвращает последние доступные результаты; если сканирование не завершилось/не удалось, это могут быть старые данные. Нужно проверять timestamp и success extra broadcast.
- Android предоставляет developer option Wi-Fi scan throttling только для локального тестирования.
- Системные/производительские реализации могут дополнительно влиять на фактическую частоту и длительность сканирования.

Официальные источники:
- https://developer.android.com/develop/connectivity/wifi/wifi-scan
- https://developer.android.com/reference/android/net/wifi/WifiManager
- https://developer.android.com/topic/performance/issues/bg-wifi

### Вывод

Главное ограничение — Android, а не скорость SQLite или локального поиска. В коде приложения 30-секундный cooldown намеренно выбран на верхней границе устойчивого foreground-лимита. Простое уменьшение его до 1–5 секунд не создаст более частых новых результатов: Android начнёт отклонять запросы/возвращать кэш, а в фоне лимит ещё строже.

### Рекомендованное ускорение без бесполезных startScan вызовов

1. Добавить lifecycle-aware receiver на `SCAN_RESULTS_AVAILABLE_ACTION` для активного мониторинга; на Android 10+ использовать также сканирования, инициированные системой/другими приложениями.
2. Сохранять timestamp и success/failure каждого broadcast; будить сбор координаты сразу после успешного свежего результата, не опрашивать `getScanResults()` каждые 250 мс.
3. Пока свежий результат не поступил, использовать последний валидный snapshot с точным возрастом, не маркировать его новым.
4. Разделить политики foreground и background: не расходовать foreground budget в цикле фонового сервиса; отображать фактический throttle state, если API доступен.
5. Оставить адаптивный cooldown: в foreground не чаще platform quota, в фоне пассивно ждать системных scan broadcasts/обновлений; не обещать периодические фоновые Wi-Fi scan чаще системного лимита.
6. В диагностику добавить: app process importance/foreground state, isScanThrottleEnabled (API 30+), startScan return, broadcast success, timestamp последнего результата, возраст кэша и время от запроса до broadcast.
7. Тестировать на конкретной версии Android/прошивке и при включённом/выключенном системном throttling; последнее — только как developer test setting.

Статус: аудит выполнен; код пока не изменён. Самый перспективный шаг — перейти с polling на receiver-driven Wi-Fi result flow и использовать пассивные полные сканирования Android.


## 14. Исправление SQLiteException в тесте карты и event-driven Wi-Fi scan

Дата: 27-11-2026. Ветка: dev. Личные данные не включены.

### Падение LocalRadioDatabaseImportTest

Симптом пользователя: `LocalListAndMapUseTheSameDatasetWithCoordinateFilteringOnly` падает с `android.database.sqlite.SQLiteException` при вызове `RadioRepository.loadMapPoints()`.

Подтверждённая причина в `LocalRadioDatabase.listMapPoints()`:
- таблица `radio_points` содержит колонку `radio_type`;
- запрос подсчёта типов использовал несуществующие `type` и `GROUP BY type`;
- запрос выборки каждой группы также использовал `WHERE type = ?`;
- список использует `SELECT *` и поэтому не обнаруживает ошибку; первый map-query падает на SQLite.

Исправлено: оба запроса используют `radio_type`. Существующий тест уже проверяет локальный список, карту, подсчёты и фильтрацию координат на 1 701 строке; отдельная новая логика для теста не требуется.

### Wi-Fi scan: переход с polling на broadcast

Изменения:
- добавлен process-scoped `WifiScanResultsMonitor`, который регистрирует `WifiManager.SCAN_RESULTS_AVAILABLE_ACTION`;
- на Android 13+ используется явный `Context.RECEIVER_EXPORTED`, чтобы получать broadcast от привилегированных системных компонентов; для более старых API используется совместимый overload;
- broadcast служит только сигналом завершения/обновления. Источником данных остаётся `WifiManager.scanResults`, а каждый результат по-прежнему проходит проверку BSSID, RSSI, timestamp и возраста;
- `collectWifi()` теперь ждёт событие до 3 секунд, а не опрашивает `scanResults` каждые 250 мс;
- учитывается `EXTRA_RESULTS_UPDATED`: false не считается свежим результатом;
- слушатель остаётся зарегистрированным на уровне application context и потому также замечает полные сканирования, инициированные системой/другими приложениями, когда процесс Clear GPS активен; последующий цикл сбора читает обновлённый системный кэш;
- сохранён 30-секундный cooldown приложения и ограничения Android. Новая схема не обещает более частые новые сканирования, чем разрешает ОС.

Добавлены Robolectric tests для успешного и неуспешного scan broadcast.

### Ограничения проверки

Изменения закоммичены в `dev`, но на момент записи не заявляется успешный локальный Gradle build или запуск на устройстве. Требуется дождаться CI для проверки компиляции, 587+ unit tests и новых receiver tests, затем проверить поведение на физическом Android-устройстве с реальной прошивкой.
