# Clear GPS

**Privacy-first Android radio surveying, local Wi-Fi/Bluetooth/cell-point mapping, and an experimental GNSS anomaly filter.**

Clear GPS is an experimental open-source Android application built with Kotlin, Jetpack Compose, Material 3 and MapLibre Native. Radio scans and recorded observations stay app-private in SQLite. Radio positioning can combine the local Wi-Fi/cell/BLE database, a cached BeaconDB estimate and cached OpenCellID cell positions; each source has its own position-use switch in **База → Источники объединённой позиции**. Network refresh is disabled by default and requires separate consent for each provider. While monitoring is active, Clear GPS checks for updates every 5 seconds but takes a fresh hardware radio snapshot no more often than every 30 seconds, respecting Android's Wi-Fi/cell/BLE throttles. BeaconDB requests a new estimate only after the stable radio-identity set changes (at least 2 minutes between changed-set requests; the same set is refreshed every 15 minutes); its result stays in a bounded in-memory cache because BeaconDB is a geolocation endpoint, not a downloadable database. OpenCellID fetches only missing/expired current-cell records into its separate SQLite table, at most 3 cells per 15-minute batch and 100 attempts per UTC day. Both providers can still be searched manually. Neither data-submission endpoint is called, and the app does not query the WiGLE API.

## Features

- **Pixel-inspired Material 3 UI** with dynamic Android 12+ colours, light/dark/system map themes, and explicit scan/status feedback.
- **MapLibre map** using OpenFreeMap styles based on OpenStreetMap data. Includes light Liberty and Dark styles, a blue location dot and accuracy area, a manual amber reference point, coloured radio-point overlays and separately named spoofing-risk zones.
- **Offline elevation data (experimental):** Settings supports manual ZIP import for user-supplied SRTM HGT tiles. Names and grid sizes are validated, and files are copied to app-private storage. No automatic DEM download is performed; terrain is not yet part of live positioning or spoofing risk.
- **Local radio recorder:** manually started scans of nearby Wi-Fi access points (BSSID + RSSI + frequency), available GSM/WCDMA/LTE/NR cell identities and BLE beacon advertisements. BLE identities are decoded from iBeacon, Eddystone-UID, AltBeacon and SemBeacon frames; RuuviTag RAWv2 sensors are decoded into stable embedded-MAC identities plus temperature, humidity, pressure, acceleration, battery and movement/sequence telemetry. Eddystone-URL and TLM metadata are decoded, while EID remains ephemeral. Random/private/anonymous MACs are never used as persistent BLE keys. Generic MAC fallback is accepted only when Android 15+ explicitly reports a public unicast address and BLUETOOTH_CONNECT is already granted; the radio scanner does not request that extra permission. Wi-Fi SSID exclusion patterns are applied both when recording observations and when estimating a position; the default `70mai*` rule is local, case-insensitive and configurable in Settings. It does not remove records already stored.
- **Private SQLite database:** Wi-Fi SSIDs and BSSIDs, available cell identifiers, stable BLE beacon protocol IDs or eligible public BLE addresses with RSSI, editable labels and coordinates, and bounded observation history. Radio identifiers remain local unless the matching external source and its network permission are both enabled. OpenCellID estimated cell-position records are fetched automatically for new/expired current cells while monitoring is active and stored in a separate `opencellid_cells` table; they are not mixed into local training observations. BeaconDB supplies a short-lived position estimate rather than a downloadable database and keeps only a bounded in-memory cache.
- **Radio-only mode:** Clear GPS stops requesting system location providers in the app and can estimate a position from the local radio database combined with available cached BeaconDB/OpenCellID estimates. Each source can be independently excluded from positioning without deleting its data. BeaconDB participates only when both its position-use switch and separate network-consent switch are enabled; during monitoring, its estimate refreshes automatically after a radio-identity change with 2-minute change cooldown and 15-minute same-identity refresh. OpenCellID uses cached current-cell records (success cache 30 days, not-found cache 7 days; records may contribute up to 90 days with growing uncertainty). OpenCellID cell estimates are deliberately coarse, with a 5 km minimum uncertainty floor. The fusion layer weights local / BeaconDB / OpenCellID as 1.00 / 0.85 / 0.30 and detects large disagreements rather than averaging them blindly. It does not switch off the GNSS hardware for Android or other apps.
- **Combined radio-source positioning:** the screen «База» contains independent switches for Local SQLite, BeaconDB and OpenCellID participation in the resulting position. The switches affect only fusion; they do not delete source records or silently enable network requests. Imported WiGLE/local sources remain independently enabled/reweighted in the existing **Источники** manager.
- **OpenCellID quota protection:** successful cell lookups are cached for 30 days and `Cell not found` for 7 days. Automatic and manual batches make at most 3 new cell queries, batches are separated by at least 15 minutes, and Clear GPS caps itself at 100 attempted API lookups per UTC day (the service's standard allowance is 1,000 credits per user/day across keys). HTTP/API quota errors halt further attempts until the app's next UTC-day budget window.
- **WiGLE interchange:** import WiGLE CSV (plain or gzip), WiGLE-style SQLite (`network` / `location` tables), or a Clear GPS SQLite backup. Export individual WiGLE observations as CSV, create a WiGLE-style SQLite database, or create a full Clear GPS backup. Imports merge with the local database; each imported file has a local source entry identified by its SHA-256 content hash, so repeating the same file reuses that source. In the database's **Источники** view, sources can be enabled/disabled, assigned a 0–100% trust weight, exported separately, or deleted with position recalculation. Each source expands into local calendar days and independent Wi‑Fi/cell/BLE records. A record shows observation/radio counts and RSSI range, can be disabled or assigned its own 0–100% trust weight, exported to CSV, or deleted without removing other dates/types. The list can be filtered by source name, date, radio type, minimum RSSI, and minimum observation count; removing a record recalculates affected positions from surviving data. Lower trust increases effective coordinate uncertainty; zero trust removes the source from estimates. Nothing is uploaded.
- **Read-only OBD-II (automatic when available):** In Auto/GPS mode, fresh PID 0D vehicle speed can briefly extrapolate a recent GPS fix when a reliable GPS course is available; in Radio mode, fresh speed can increase local radio scan cadence while moving. After checking the Mode 09 support bitmap, the screen reads the VIN (InfoType 02) only if the ECU advertises it. The VIN stays in connection memory and is displayed locally; it is not persisted, logged, exported or sent over the network. When the ECU advertises support, the screen can also show standard PIDs for RPM (0C), calculated engine load (04), coolant temperature (05), manifold pressure (0B), throttle position (11), and barometric pressure (33). A GNSS-vs-OBD comparison can learn a bounded session-only speed correction from at least 20 well-aligned trusted physical-GPS pairs spanning 30 seconds and varied speeds. Until stable, the coefficient is only a candidate. It is cleared on disconnect, is not keyed by VIN, and affects only the short-lived speed passed to bounded extrapolation; disagreement alone never raises spoofing risk. OBD polling adapts to movement: about 3.5 seconds at a valid stationary idle, 1.5 seconds while moving, 2 seconds when speed is unknown, and 5 seconds when PID 0D is unsupported/disabled. The current connection also estimates distance by integrating fresh speed samples and shows smoothed longitudinal acceleration; these are not an odometer or stored trip history and do not affect spoofing risk. These extra values are displayed locally by default and are not persisted or fed to position fusion. An explicit OBD-screen switch can opt into a custom Android broadcast (`org.cleargps.action.OBD2_TELEMETRY`) for compatible receiving apps; broadcast values are timestamped and freshness-limited, and VIN/adapter address are never sent. This is not a universal Android vehicle-data API: a receiving app must implement this action. Unsupported or malformed readings are isolated per PID. OBD-II remains optional and has no separate positioning mode. Bluetooth Classic SPP and BLE GATT with common writable/notify characteristic layouts are supported; proprietary variants may still fail. Wi-Fi TCP is supported when the user manually joins the adapter's Wi-Fi network and enters a private IPv4 address/port; the socket is bound only to the Wi-Fi subnet containing that address, and Internet access may be unavailable on the adapter AP. USB is not yet supported.
- **Risk-zone management:** draw multiple named polygons, rename/delete them and enable/disable each zone. These polygons are enforced in GNSS trust, radio-position read paths and the SQLite write path; blocked scans do not create radio-point or observation rows.
- **Airport exclusion:** a bundled offline catalogue contains 29,308 airport/landing-strip locations (ICAO/IATA identifiers and coordinates), sourced from [mwgg/Airports](https://github.com/mwgg/Airports) under its MIT licence. The default exclusion radius is 2 km and can be changed from 200 m to 20 km; the feature can be disabled and individual airport codes can be excluded. A position inside the buffer is excluded from radio matching and recording. Airport proximity contributes only 10 heuristic risk points and never sets the hard `ZONE_RISK` state by itself. If the bundled catalogue is missing or older than 30 days, an optional HTTPS GET fallback downloads the public [OurAirports CSV](https://davidmegginson.github.io/ourairports-data/airports.csv) after the separate catalogue-consent switch is enabled; the refreshed list is cached locally. No device coordinates or radio identifiers are sent in that request.
- **Continuous fix control and system delivery:** the main “Enable fix” button starts/stops the foreground location service and mock output. Calculated fixes are sent to Android's system fused provider and, when Google Play services is available, to Fused Location Provider clients. In GPS/Auto modes the physical GPS provider is kept intact so Clear GPS can continue filtering real GNSS input; direct clients explicitly requesting GPS may therefore still read the physical fix. Radio-only mode can replace GPS and network providers because it does not consume them as inputs. Android marks these locations as mock, and some apps deliberately ignore them. The refresh interval is configurable from 1 to 30 seconds; radio scans remain subject to Android throttling. Recording observations is still a separate switch.
- **Reboot and service recovery:** monitoring is restored after reboot only if it was enabled before reboot and Android has granted Clear GPS “Allow all the time” location access. A WorkManager watchdog checks a local monotonic service heartbeat at a minimum interval of 15 minutes and queues a delayed check after the app task is dismissed or the service is destroyed. Recovery is attempted only for previously enabled monitoring and with location/background-location permissions. Android or OEM background-start restrictions may still block it; the status then asks the user to open Clear GPS and tap Enable fix. This is best-effort recovery, not a guarantee of uninterrupted tracking.
- **Battery optimization:** Settings includes a user-triggered system request to exempt Clear GPS from Doze/App Standby optimization for long-running location monitoring. The prompt is never opened automatically; the user can decline, and the exemption can increase battery use. If the direct request screen is unavailable, the app falls back to Android’s general battery-optimization list or app details. Clear GPS does not hold a permanent wake lock.
- **Guarded fallback:** previously recorded radio estimates are considered only when recent, matched against enough local points and within a conservative accuracy threshold. A manual reference can be enabled as a final, coarse fallback. Cached scans do not refresh the last-confirmed mock-fix timer; if fresh publication stops, the service removes the stale mock provider after a bounded 30–90 second watchdog window. Diagnostic messages distinguish heard radios, identifiers found in the database, and entries with usable coordinates.
- **Storage and map limits:** detailed radio-observation history defaults to 20,000 rows and has selectable retention limits of 5,000, 10,000, 20,000 or 50,000 (maximum 50,000). Lowering this setting prunes the oldest detailed observations but preserves radio-point summaries and their selected coordinates. Scan history is capped at 500 entries. Separately, the saved map-marker limit defaults to 50,000 geolocated radio points and can be set to 5,000, 10,000, 20,000, 50,000, 100,000, 250,000 or 500,000. There is no hidden low-RAM/device-class cap; points without valid coordinates are not plotted. Wi-Fi, cell and BLE map layers are clustered. Higher map limits use more memory and may slow rendering.
- **Memory-aware Windows build:** Gradle heap is sized from installed/free RAM with a safety reserve for Windows; the daemon, parallel execution and build cache are enabled.
- **Fix cadence and battery profile:** the configured interval is 1–30 seconds. Eco doubles the resulting fix/radio interval, Normal preserves it, and Max halves it (with a one-second minimum); optional movement adaptation is applied first. The profile only adjusts scheduled fix requests and repeat radio searches; raw GNSS callbacks are not throttled, so the detector can retain its evidence. Android may throttle actual Wi-Fi/Bluetooth scans, and no battery percentage-per-hour figure is claimed before reference-device measurements.
- **Private map fallback:** a tile-free offline canvas retains local radio markers without requesting map data, but does not display streets or labels.
- **GNSS diagnostics:** live in-memory sky plot and per-satellite C/N₀, constellation, elevation/azimuth, used-in-fix status and frequency when Android reports it; AGC appears per satellite or per band only when the device/Android API supplies it. Detailed satellite readings are not persisted by default; opt-in replay recording is available with a 2 MiB cap, relative (non-world) track coordinates and manual export. Version 2 also records available phone IMU samples (up to 5 samples/s per type) and anonymized Wi-Fi/cell/BLE observations only while monitoring in Auto mode, no more often than every 15 seconds (or the longer configured interval). Real BSSID, SSID, cell IDs and BLE addresses are replaced with opaque IDs scoped to the recording. The replay viewer reports these samples, but IMU and radio do not currently affect the live risk estimate. Users can label a suspicious event as a false alarm or justified suspicion and optionally export a privacy-minimized JSON dataset; labels never train/change the live detector automatically.
- **Device capabilities:** Settings shows GPS-provider state, live raw-GNSS/AGC evidence, observed carrier-frequency bands, pressure sensor, Wi-Fi RTT availability, accelerometer, gyroscope and magnetometer. Unknown live GNSS evidence is displayed as unknown rather than as a broken sensor; the report does not start scans or request permissions.
- **Windows build script** and GitHub Actions workflow for unit tests and debug APK generation.
- **Debug-only performance diagnostics:** StrictMode logs potential main-thread I/O and VM/resource violations to Logcat without crashing the app. LeakCanary 2.14 watches destroyed Android components in debug builds only; neither the LeakCanary library nor its heap analysis is included in release builds.

## Radio positioning and WiGLE

WiGLE is supported as a **local file interchange format**, not as a remote database dependency. Import a CSV (plain or gzip) or a SQLite database exported by WiGLE; the importer recognises the `network` summary and `location` observation tables. SQLite imports are validated and merged into the current database rather than replacing it. Imported sources are shown separately in **Источники** and can be excluded, reweighted, exported or removed without deleting other sources. The export menu offers three distinct outputs: WiGLE CSV (one row per retained observation, plus a representative row for a radio with no history), a WiGLE-shaped SQLite database (`network` and geolocated `location` rows), and a full Clear GPS SQLite backup (radio summaries, observation history, and scan history). WiGLE-shaped exports omit unlocated observations because the WiGLE `location` format requires coordinates; use the full Clear GPS backup to preserve all app history. Identifiers are normalized to lowercase and duplicate observations are skipped when the same file is imported again. Clear GPS never asks for a WiGLE username/API key and never uploads selected files.

A Wi-Fi/Bluetooth identifier by itself does not reveal coordinates. For radio-only navigation, first record scans at places with known coordinates, use a manual reference as coarse training data, or import a compatible WiGLE CSV. The local estimator prioritizes **radio fingerprint matching** across complete recorded scans and falls back to geolocated local radio points when no suitable fingerprint exists. The source-fusion layer then combines that independent local estimate with a matching cached BeaconDB estimate (2-minute TTL, 10 dB RSSI buckets) and the current cells' cached OpenCellID cell-position estimates when each source is enabled. BeaconDB and OpenCellID can refresh automatically during active monitoring only after their separate network permissions are enabled; periodic checks run every 5 seconds, while hardware snapshots are capped at 30 seconds and external requests have independent cooldowns. Provider estimates are weighted by their uncertainty and source trust; large disagreements select the strongest weighted estimate and increase the reported uncertainty. OpenCellID positions are community-derived estimates of cell records, not surveyed antenna locations or phone positions. Their effect is deliberately weak and carries a minimum 5 km uncertainty. The fused estimate is not written back as training ground truth, avoiding self-reinforcing drift. Moved access points, changing radio conditions, sparse external coverage or missing Android CellInfo can still cause missing or wrong fixes.

## Read-only OBD-II foundation

OBD-II connects only after the user opens its screen and selects a previously paired Classic SPP adapter or a BLE candidate discovered by pressing the explicit BLE-scan button. Entering the screen never starts BLE discovery automatically. The BLE scan lasts 8 seconds and keeps likely OBD-like candidate names in memory. The candidate list, names and advertisement data are not persisted; the selected BLE adapter key may be saved locally like the Classic selection so the same adapter can be targeted for reconnect. Nothing from the scan is uploaded. Android's Nearby devices / `BLUETOOTH_CONNECT` permission is used to connect, and `BLUETOOTH_SCAN` is requested only for that explicit BLE search. After a previously successful, user-requested session loses its link, Clear GPS retries only that same paired adapter up to five times with bounded backoff; manual disconnect cancels retries, and Bluetooth-off/permission/configuration failures stop retrying. An initial failed connect does not start a retry loop.

The client follows the standard SAE J1979 Mode 01 capability-bitmap chain (`00`, `20`, `40`, `60`, `80`, `A0`, `C0`) only while each page advertises the next page. Once per connection it separately checks the Mode 09 InfoType `00` bitmap and requests VIN InfoType `02` only when that bit is advertised. It supports the single CAN payload and ordered legacy multi-frame responses; malformed or partial VIN data is rejected. It then reads only allowlisted telemetry PIDs that the ECU reports as supported: 04 (calculated engine load), 05 (coolant temperature), 0B (manifold pressure), 0C (engine RPM), 0D (vehicle speed), 11 (throttle position), and 33 (barometric pressure). If the first bitmap is absent or unusable, it probes PID 0D only; if a later bitmap is malformed, the already decoded capabilities are retained. Unsupported PIDs are skipped, and arbitrary requests remain blocked. One isolated zero speed/RPM sample shortly after a positive sample is withheld as missing data; a second consecutive zero is accepted, so a genuine stopped engine/vehicle is not hidden indefinitely. A malformed but framed reply is discarded independently for its PID; three consecutive invalid replies disable only that PID for the current connection session, and a valid reply resets that PID's failure streak. Reconnecting starts fresh breakers. Link-level timeouts or stream failures end the connection instead of risking a desynchronized byte stream. Only fresh PID 0D speed is passed to position fusion; the other parameters remain in screen memory and are not persisted. The selected GPS/radio positioning source continues without OBD-II assistance if speed is unavailable. The screen shows a status explaining the failure and fallback.

Only fresh PID 0D speed contributes to position fallback. When Auto/GPS mode is selected and a connected OBD-II adapter provides fresh speed, the **map** can extrapolate for at most 30 seconds from a recent GPS fix, only when that fix has a course, reported GPS accuracy is at most 100 metres, and speed data is no more than 5 seconds old; projected travel is capped at 300 metres and estimated uncertainty grows with time and distance. If those conditions fail, the map reverts to the current GPS fix or stops presenting it as fresh rather than guessing a direction. When the foreground monitor is running, it can also publish that bounded prediction through the mock GPS provider **only if mock-location output was explicitly enabled**, the last fix was accepted as NORMAL by the GNSS filter, and the position is outside risk zones. The prediction is not fed back to the spoofing detector; an alert, stale input, excessive projected distance or a new source mode stops and clears it. When Radio mode is selected, the local radio database remains the only coordinate source and fresh OBD speed may shorten radio scan intervals while moving. Vehicle speed alone cannot determine a position. The latest speed sample is handed between the app and foreground service through a timestamped preference and is considered usable for only 5 seconds; it is not a trip history and is cleared on disconnect. Transports include Bluetooth Classic RFCOMM/SPP and partial BLE GATT support for common writable/notify characteristic layouts (including Nordic UART and common FFE0/FFF0-style services). Some proprietary clones or services with unusual characteristic layouts may not work; Wi-Fi TCP works with a manually entered private IPv4 address and port, but the phone must already be joined to the adapter Wi-Fi network. Clear GPS binds only its TCP socket to the local Wi-Fi subnet and does not switch networks automatically; Internet may be unavailable on the adapter AP. USB remains unsupported. A session-only panel estimates distance from fresh speed samples and displays smoothed longitudinal acceleration. It is neither an odometer nor a stored trip history; unknown gaps are not guessed, and these metrics do not affect spoofing risk.

While the TrustEngine is in `NORMAL`, Clear GPS also observes repeatable engine-RPM / vehicle-speed ratio bands from time-aligned, individually timestamped PID 0C and 0D replies. This is session-only diagnostic learning: bands are not saved as a vehicle profile, do not affect spoofing risk, and are not presented as actual gear numbers because tyre circumference and final-drive ratio are not known. Samples are accepted only while the trusted GNSS↔OBD speed pair is valid; slow, stale, misaligned, or high-load samples are skipped.

## Privacy and network traffic

- **BeaconDB is opt-in and disabled by default.** When separately enabled, a background fix may refresh `https://api.beacondb.net/v1/geolocate` after the radio identity set changes; the identity set is hashed before being stored for cooldown scheduling. The contribution endpoint is never used. No WiGLE API requests run.
- **Short-lived BeaconDB cache.** Successful estimates are reused for up to 2 minutes when supported identifiers and coarse RSSI buckets match. Small signal changes stay in the same 10 dBm bucket. The cache key is a SHA-256 digest, entries are bounded and held only in process memory, and cache hits do not make an HTTP request. The cache writes neither cell identifiers nor estimates to SQLite and is not used for radio training; it disappears when the process exits.
- **No automatic upload.** Scans, labels, coordinates, zones and history are stored locally in app-private SQLite/preferences.
- **Crash-loop safety.** After three uncaught crashes within ten minutes, Clear GPS enters a ten-minute safe mode and disables BeaconDB lookup/mock output. Its preference is switched off and must be explicitly enabled again. A minimal `CRASH` record is always written to the private diagnostics log, even when verbose logging is off; it stores the exception type and up to eight stack frames (class/method/line), not the exception message.
- **Undo for source history deletion.** Deleting a source/day or source/day/radio-type segment offers a short-lived Snackbar Undo action that restores deleted rows transactionally. The snapshot stays private to SQLite, expires after two minutes, and is discarded when dismissed or when another database mutation starts.
- **Local radio identifiers.** SSIDs and BSSIDs are stored in the private local database for search and editing. Bluetooth names and advertisement payloads are not persisted by Clear GPS. A manual BLE OBD search temporarily reads recognizable device names in memory; the candidate list and names are not saved or exported. The selected BLE adapter key is stored locally in preferences for reconnect, just like a selected Classic adapter; no BLE scan data is uploaded. SSIDs, BSSIDs, cell IDs and BLE addresses are never added to map requests or uploaded by Clear GPS.
- **Maps are still online by default.** OpenFreeMap serves map styles/tiles from its public service, so ordinary map requests expose the device's IP address and which map area is being viewed to that map provider. Wireless identifiers are not attached to those requests. For more private use, the map component must be pointed at a self-hosted or offline map source.
- **Permissions matter.** Android can throttle Wi-Fi scans, limit cell information, randomize Bluetooth addresses, and refuse scans when permissions or system settings do not allow them. Turning off global Android location can also block Wi-Fi scanning on some versions/devices.
- **Radio-only is an app-level mode.** A regular Android application cannot force the system-wide GNSS hardware switch off without privileged/system access. Clear GPS can stop requesting GPS updates itself; supplying locations to other apps additionally requires selecting Clear GPS as the mock-location app in Developer options. Some apps detect or ignore mock locations.
- The app is experimental and does not guarantee accurate navigation or detect every kind of GNSS spoofing.

## Build on Windows

Run **build-apk.bat** from the repository root. The helper checks for a compatible Java/Android SDK/Gradle setup and can offer to install missing tools after confirmation. It verifies downloaded archive hashes when supported by the bootstrap script.

After a successful build, the APK is written to **dist/ClearGPS-debug.apk**. You can also download the **ClearGPS-debug** artifact from the [GitHub Actions runs](https://github.com/MAKAKAIglitch/clear-gps/actions).

## Maps and attribution

The default map styles are supplied by [OpenFreeMap](https://openfreemap.org/) and use OpenMapTiles / OpenStreetMap data. Attribution is shown in the app. OpenFreeMap's public styles are convenient but require internet access; consult its current [terms](https://openfreemap.org/tos/) before adding offline downloads or larger-scale caching. No map tiles are bundled in the APK.

## Development status

This is a research/learning project. The app has automated build and unit-test checks, but the full scan/record/edit/radio-only workflow still needs hands-on validation on real Android devices and different manufacturers. The stated accuracy radius of a local estimate is heuristic rather than a surveyed guarantee.

# Русский

**Clear GPS — экспериментальное Android-приложение для локальной записи Wi-Fi/Bluetooth/сотовых радиоточек, навигации по собственной базе и фильтрации GNSS-аномалий.**

Проект построен на Kotlin, Jetpack Compose, Material 3 и MapLibre Native. Радиоидентификаторы и локальные наблюдения остаются в приватной SQLite-базе приложения. Сетевые обновления выключены по умолчанию и требуют отдельного разрешения для каждого источника. При включённом фиксе приложение проверяет обновления раз в 5 секунд, но снимает новые радиоданные не чаще раза в 30 секунд с учётом ограничений Android. BeaconDB получает новый geolocation-запрос при изменении набора радиоидентификаторов с паузой не менее 2 минут; OpenCellID загружает только отсутствующие/устаревшие записи текущих сотовых ячеек — до 3 за 15 минут и до 100 попыток в сутки. BeaconDB хранит только краткоживущий кэш оценки в памяти, а OpenCellID — отдельный каталог SQLite. В WiGLE API приложение не обращается и endpoint отправки вкладов BeaconDB не вызывает.

## Возможности

- **Интерфейс в духе Pixel / Material 3:** динамические цвета Android 12+, темы карты «система / светлая / тёмная», понятные статусы сканирования.
- **Карта MapLibre** на основе OpenFreeMap и данных OpenStreetMap: тёмная и светлая темы, синяя точка позиции с радиусом точности, янтарный ручной ориентир, цветные радио-точки и несколько именованных зон риска.
- **Локальный сканер:** Wi-Fi BSSID/уровень сигнала/частота, доступные Android идентификаторы сотовых сот GSM/WCDMA/LTE/NR, BLE-маяки iBeacon, Eddystone, AltBeacon, SemBeacon и сенсоры RuuviTag RAWv2. Ruuvi выдаёт устойчивый MAC внутри payload и телеметрию температуры, влажности, давления, ускорения, батареи и движения. Для остальных форматов координатные ключи берутся из устойчивых полей протокола, а не меняющегося рекламного MAC; обычный MAC допускается только как публичный адрес, явно подтверждённый Android 15+, при уже выданном BLUETOOTH_CONNECT; BLE-сканер сам не запрашивает это дополнительное разрешение.
- **Локальная SQLite-база и выбор источника:** по умолчанию открывается локальная база; вкладка «База» также показывает BeaconDB и отдельный OpenCellID-каталог. При включённом фиксе BeaconDB обновляет краткий кэш оценки по изменившимся радиоидентификаторам, а OpenCellID автоматически добавляет неизвестные или просроченные текущие ячейки; обе функции требуют отдельных включённых разрешений и отключаются независимо.
- **Режим «Только радио»:** Clear GPS перестаёт запрашивать системные провайдеры геолокации и рассчитывает положение только при совпадении текущих радиосигналов с координатными точками локальной базы. Режим не выключает GNSS-модуль для всей системы Android.
- **Обмен с WiGLE:** импорт CSV (обычный или gzip), WiGLE SQLite (`network` / `location`) и резервных копий Clear GPS; экспорт CSV по отдельным наблюдениям, WiGLE-совместимой SQLite и полной SQLite-копии Clear GPS. Импорт объединяет данные и не дублирует уже имеющиеся наблюдения.
- **Основа OBD-II только для чтения:** подключение по запросу к уже сопряжённому Bluetooth Classic SPP адаптеру; скорость 0D остаётся единственным автомобильным параметром, используемым для прогноза позиции. При подключении приложение один раз проверяет битовую карту Mode 09 и запрашивает VIN (InfoType 02) только если ЭБУ объявил его поддержку. VIN находится только в памяти текущего соединения и отображается на экране; он не сохраняется, не попадает в логи/экспорт и не отправляется по сети. При наличии поддержки ЭБУ экран дополнительно показывает стандартные PID оборотов 0C, нагрузки 04, температуры 05, MAP 0B, дросселя 11 и барометрического давления 33. Сверка GNSS↔OBD обучается только на физических GPS-фиксах в состоянии доверия NORMAL, с контролем погрешности и монотонных меток времени. Поправка включается после минимум 20 согласованных пар за 30 секунд и достаточного диапазона скоростей; коэффициент ограничен 0,88–1,12 и сбрасывается при отключении. Расхождение само по себе не повышает риск спуфинга. За время подключения приложение также оценивает путь интегрированием свежих скоростей и сглаженное продольное ускорение; это не одометр и не история поездки, данные не сохраняются и не влияют на риск спуфинга. Дополнительные значения по умолчанию остаются в памяти экрана и не записываются в историю. Отдельный переключатель на экране OBD-II разрешает отправку свежих показаний через Android broadcast `org.cleargps.action.OBD2_TELEMETRY` для совместимых приложений-получателей. Пакет содержит метки времени; VIN и адрес адаптера не передаются. Это не универсальный Android API телеметрии автомобиля: принимающее приложение должно поддерживать это действие. Bluetooth Classic SPP и BLE GATT с распространёнными характеристиками записи/уведомлений поддерживаются частично; некоторые фирменные варианты BLE-клонов не заработают. Wi-Fi TCP поддерживается при ручном подключении к сети адаптера и вводе приватного IPv4/порта; приложение привязывает TCP-сокет только к Wi-Fi-подсети целевого адреса и не переключает сеть автоматически. На точке доступа адаптера интернет может быть недоступен. USB пока не поддерживается.
- **Зоны спуфинга:** рисование нескольких полигонов, переименование, удаление и отдельное включение каждой зоны.
- **Кнопка фикса и передача в приложения:** «Включить фикс» запускает foreground-сервис и публикацию рассчитанных координат через системный fused-провайдер Android и Google Fused Location Provider (если доступны Google Play services); отдельный статус показывает результат этой передачи. В режимах «GPS» и «Авто» настоящий GPS-провайдер не подменяется, иначе приложение перестало бы получать новые физические GNSS-фиксы для фильтрации. Поэтому приложения, которые напрямую запрашивают именно GPS-провайдер, могут по-прежнему видеть исходный GPS; приложения, использующие fused location, получают вычисленную позицию. В режиме «Только радио» можно дополнительно подменять GPS и network-провайдеры, поскольку они не используются как входы. Android помечает такие позиции как mock, и некоторые приложения намеренно их игнорируют. Интервал обновления настраивается от 1 до 30 секунд. В режиме GPS радиосканирование, запись и отображение радио-точек отключены; GNSS-фильтр работает независимо от локальной радиобазы.
- **Возможности устройства:** отдельный раздел настроек показывает состояние GPS-провайдера, свежие данные raw GNSS/AGC, наблюдавшиеся частотные диапазоны, барометр, Wi-Fi RTT, акселерометр, гироскоп и магнитометр. Неподтверждённые GNSS-возможности отмечаются как неизвестные; экран не запускает сканы и не запрашивает новые разрешения.
- **Диагностика mock location:** настройки показывают, включён ли запрос фикса и подтвердил ли Android публикацию тестового провайдера. Для передачи координат нужно выбрать Clear GPS как приложение фиктивного местоположения в настройках разработчика. В режиме «Только радио» локальная оценка публикуется через GPS- и сетевой mock-провайдеры, чтобы её получали приложения, запрашивающие любой из этих источников; в GPS/«Авто» сетевой провайдер не подменяется, чтобы сохранить системный источник фильтра. Отдельная кнопка в просмотре BeaconDB позволяет вручную опубликовать готовую cell-only оценку через оба mock-провайдера на 2 минуты; повторных запросов BeaconDB она не делает, а радиус погрешности увеличивается по времени. Android помечает такие координаты как mock, и отдельные приложения могут их игнорировать.
- **Разметка событий риска:** в раскрываемой GNSS-диагностике можно отметить подозрительное событие как ложную тревогу или как обоснованное подозрение. Метки хранятся только на устройстве (не более 200), не меняют работающий детектор и по отдельному действию экспортируются в JSON без координат, радиоидентификаторов, сырых измерений и абсолютного времени.
- **Запись GNSS и реплей:** после отдельного подтверждения записываются спутниковые GNSS-поля, GPS/network-трек в относительных координатах и доступная IMU (до 5 образцов/с на тип). Только в режиме «Авто» во время активной записи дополнительно собираются Wi‑Fi, сотовые и BLE-наблюдения с интервалом не чаще раза в 15 секунд (или реже согласно настройке); в режиме GPS дополнительных радио-сканов нет. В формате v2 исходные BSSID, SSID, ID сотовых ячеек, BLE MAC и протокольные ID маяков заменены порядковыми ID, действующими только внутри одной записи. Файл остаётся в закрытом хранилище до ручного экспорта, ограничен 2 МиБ/50 000 строк, формат v1 остаётся читаемым. Календарные времена и абсолютные координаты не сохраняются. Трек, датчики и последовательность радио-наблюдений всё ещё могут раскрывать контекст движения. IMU и радио пока не влияют на риск.
- **Журнал ошибок:** в настройках → «Прочее и диагностика» можно включить подробные локальные журналы, ограничить размер от 64 до 512 КБ, открыть журнал, очистить его или скопировать актуальный текст целиком. Логирование выключено по умолчанию. Перед записью и при чтении старого файла распознаваемые SSID/BSSID/MAC, имена/адреса устройств, помеченные ID сотовых ячеек и BLE-адреса маскируются; координаты в явных полях и парах округляются до сотых градуса (порядка 1 км). Свободный текст произвольного формата нельзя гарантированно классифицировать, поэтому сообщения журнала не должны включать сырые радиоданные. Минимальная запись о падении сохраняется всегда, даже если подробное логирование выключено: тип исключения и до 8 кадров стека (класс/метод/строка), без сообщения исключения. После трёх необработанных падений за 10 минут включается безопасный режим на 10 минут, а BeaconDB выключается и требует явного повторного включения. Полная SQLite-резервная копия экспортируется отдельным осознанным действием и может содержать точные радиоидентификаторы, координаты и историю наблюдений.
- **Ограничение объёма данных:** лимит подробных радио-наблюдений настраивается в экране локальной базы: 5 000, 10 000, 20 000 или 50 000 последних наблюдений. При уменьшении лимита удаляется только самая старая подробная история RSSI/частоты; сводные радиоточки и их координаты сохраняются. История сканирований ограничена 500 записями, на карте одновременно показывается не более 400 сохранённых радио-точек.
- **Перенос настроек и зон:** в «Настройки» → «Дополнительно и данные» можно вручную экспортировать или восстановить файл `.cgsettings` версии 2. Он содержит режим положения, тему/источник карты, интервал, профиль Eco/Normal/Max, переключатели Wi‑Fi/сот/BLE и зоны риска с их координатами; старые файлы версии 1 продолжают импортироваться с профилем Normal. Это отдельный файл, не резервная копия радиобазы: для базы используй полный Clear GPS SQLite backup. Импорт после подтверждения заменяет эти настройки и список зон; он не переносит ручной ориентир, лимит истории, диагностические логи, разрешение BeaconDB, состояние мониторинга/mock или replay-запись.
- **Сборка с учётом ОЗУ:** heap Gradle рассчитывается по доступной/установленной памяти с резервом для Windows; включены daemon, параллельная сборка и кэш.
- **Восстановление службы:** мониторинг восстанавливается после перезагрузки только если он был включён и выдано разрешение геолокации «Всегда». Локальный watchdog WorkManager проверяет монотонный heartbeat с минимальным периодом 15 минут и ставит отложенную проверку после удаления задачи из недавних приложений/уничтожения службы. Он не включает мониторинг самовольно и требует разрешений геолокации; Android или прошивка всё равно могут запретить фоновый запуск. В таком случае статус предлагает открыть Clear GPS и нажать «Включить фикс». Это best-effort, а не гарантия непрерывного трекинга.
- **Оптимизация батареи:** в настройках есть явная кнопка системного запроса на исключение Clear GPS из оптимизации Doze/App Standby для длительного мониторинга геолокации. Окно не появляется автоматически; пользователь может отказать, а исключение может увеличить расход батареи. Если прямой запрос недоступен, приложение открывает общий список оптимизации батареи или настройки Clear GPS. Постоянный wake lock не удерживается.
- **Частота фикса:** интервал 1–30 секунд; при включённой адаптации интервал может уменьшаться в движении. Фактическая частота радиообновлений зависит от системных ограничений Android. Кэшированные сканы не продлевают таймер последнего подтверждённого mock-фикса; если свежая публикация прекратилась, watchdog удаляет устаревший mock-провайдер через ограниченное окно 30–90 секунд. Диагностика отдельно показывает услышанные радиосигналы, найденные в базе идентификаторы и записи с пригодными координатами.
- **Приватный режим карты:** офлайн-холст не запрашивает тайлы, но показывает локальные радиоточки без улиц и подписей.
- **Сборка для Windows** и GitHub Actions для тестов и создания debug APK.
- **Диагностика debug-сборки:** Android StrictMode пишет потенциальные нарушения главного потока и VM/ресурсов в Logcat, не завершая приложение. LeakCanary 2.14 отслеживает удерживаемые после уничтожения Activity/Service только в debug-варианте; библиотека и анализ heap не попадают в release APK.

## Локальная навигация и WiGLE

WiGLE поддерживается как **локальный файловый формат**, а не как удалённый сервис. BeaconDB не предоставляет публичный полный дамп для скачивания: её публичный API возвращает оценку местоположения по предоставленным данным ячеек, а не каталог всех записей. Поэтому вкладка BeaconDB — это отдельный ручной cell-only поиск, не синхронизация и не импорт серверной базы. Можно импортировать CSV (обычный или gzip) либо SQLite-базу WiGLE; распознаются таблицы `network` (сводка сетей) и `location` (отдельные наблюдения). Импорт SQLite проверяется и объединяется с текущей базой, а не заменяет её. Меню экспорта предлагает три разных файла: WiGLE CSV (строка на каждое сохранённое наблюдение и одна сводная строка для точки без истории), WiGLE-совместимую SQLite с таблицами `network` и `location`, а также полную резервную копию Clear GPS SQLite с радиоточками, историей наблюдений и историей сканирований. В WiGLE-форматы не включаются наблюдения без координат, поскольку формат таблицы `location` требует координаты; для сохранения всей истории приложения используй полную резервную копию Clear GPS. Идентификаторы приводятся к нижнему регистру, повторный импорт того же файла не должен добавлять одинаковые наблюдения. Clear GPS не запрашивает WiGLE API key и не отправляет выбранные файлы на сервер.

Один Wi-Fi/Bluetooth идентификатор сам по себе не даёт координат. Для радионавигации сначала запиши сканирования в местах с известным положением, используй ручной ориентир как грубую учебную точку или импортируй совместимый WiGLE CSV. Clear GPS в первую очередь применяет **сопоставление радиоснимков**: сравнивает текущие идентификаторы и RSSI с полными сканированиями из локальной базы, учитывает тип радио и различия уровня сигнала, затем объединяет близкие качественные совпадения. Если подходящего отпечатка нет, используется запасной расчёт по координатам радиоточек с ограничением влияния каждого типа радио, ослабленным влиянием RSSI и отбрасыванием пространственных выбросов. Если почти одинаковый отпечаток найден в удалённых местах, алгоритм отказывается угадывать. Результат режима «Только радио» не записывается обратно как достоверная учебная координата — это предотвращает накопление ошибки от самоподкрепления. Для точек, которые не закреплены вручную и не импортированы из WiGLE, новый максимум RSSI всё ещё может уточнить примерное место приёма, если исходный ориентир имеет точность не хуже 50 м; это не триангуляция и не гарантия координат антенны. Расчёт остаётся эвристическим и требует ранее записанных сканирований с координатами. Перестановка точек доступа, изменение радиосреды или малое число совпадений могут привести к отсутствию позиции или ошибке. Для запасного расчёта координатные Wi-Fi/сотовые записи могут использоваться до 5 лет, а BLE — до 180 дней; возраст добавляет штраф к погрешности, поэтому старые записи не считаются столь же надёжными, как свежие. Сканирования ячеек сотовой сети старше 5 минут отбрасываются по метке времени. Идентификаторы сотовых сот доступны только когда их предоставляет Android; без локальных координат они не превращаются в геолокацию автоматически.

## Основа OBD-II только для чтения

Первичное подключение OBD-II выполняется по действию пользователя: выбрать ранее сопряжённый Classic SPP-адаптер или BLE-кандидат, найденный отдельной кнопкой поиска, либо вручную добавить Wi-Fi TCP endpoint после подключения к сети адаптера в настройках Android. После успешного подключения Clear GPS запоминает последний endpoint и включает переключатель «Автоподключение к последнему адаптеру». При следующем запуске/возврате приложения выполняется попытка соединения, если уже выдано разрешение Bluetooth; при временном обрыве повтор продолжается с паузами 1, 2, 4, 8, 15, 30 и 60 секунд, затем не чаще раза в минуту, пока пользователь не выключит переключатель или не отключит адаптер вручную. Временная ошибка первой попытки также запускает повторы. Ошибки разрешений и конфигурации не повторяются в плотном цикле; разрешение можно выдать в Android, после чего попытка возобновится при возврате в приложение. BLE-поиск при запуске не выполняется: сканирование длится 8 секунд и доступно только вручную. Wi-Fi TCP повторяется только для сохранённого приватного endpoint и только после того, как пользователь подключил телефон к сети самого адаптера; сеть телефона приложение не переключает.

Сначала приложение последовательно проверяет битовые карты возможностей SAE J1979 Mode 01 PID `00`, `20`, `40`, `60`, `80`, `A0`, `C0` — только пока предыдущая карта объявляет следующий диапазон. Отдельно один раз за соединение проверяется карта Mode 09 InfoType `00`; запрос VIN InfoType `02` выполняется только если соответствующий бит указан как поддерживаемый. Коэффициент калибровки ограничен диапазоном 0,88–1,12; он включается только после устойчивой выборки и применяется только к короткоживущей скорости для вспомогательного счисления пути, не к детектору спуфинга. Обрабатываются одиночный CAN-ответ и упорядоченные старые многокадровые ответы; неполный или некорректный VIN отклоняется. Затем читаются только разрешённые стандартные PID, поддержку которых объявил ЭБУ: 04 (расчётная нагрузка), 05 (температура охлаждающей жидкости), 0B (давление во впускном коллекторе), 0C (обороты), 0D (скорость), 11 (положение дросселя) и 33 (барометрическое давление). Экран «Трассировка PID → потребители» показывает значение, состояние, возраст и реальные внутренние потребители: PID 0D участвует в проверке скорости для антиспуфинга, калибровке GNSS↔OBD, коротком GPS-прогнозе и адаптивном интервале сканирования; PID 0C совместно с PID 0D, а также фильтры нагрузки PID 04/дросселя PID 11 используются для временно согласованного обучения отношений RPM/скорости. PID 0B/05/33 сейчас отображаются и доступны в отдельно включаемом broadcast, но пока не участвуют во внутреннем расчёте позиции или риска; подключение барометрической ветки — P3.6. Если первая карта отсутствует или некорректна, приложение безопасно проверяет только скорость 0D; при повреждении последующей карты сохраняются уже распознанные возможности. Неподдерживаемые PID пропускаются, произвольные запросы запрещены. Одиночный нулевой ответ скорости/оборотов вскоре после ненулевого измерения временно пропускается как отсутствующее значение; повторный ноль принимается, поэтому реальная остановка автомобиля или двигателя не скрывается бесконечно. Три подряд некорректных, но завершённых ответа отключают только соответствующий PID до переподключения; валидный ответ сбрасывает его серию ошибок. Таймаут и потеря Bluetooth-соединения завершают сессию, чтобы не использовать потенциально рассинхронизированный поток. Только свежая скорость PID 0D передаётся в алгоритм позиции; остальные показатели отображаются локально и не сохраняются в истории. Если скорость недоступна, GPS/радиопозиционирование продолжает работать самостоятельно.

**Фактические потребители PID:** PID 0D передаётся в `LocationMonitorService` как вспомогательный признак скорости GNSS-фильтра, в `Obd2LocationFusion` для короткой экстраполяции последнего GPS-фикса, в `Obd2SpeedCalibration` и `BatteryProfilePolicy`; отдельная оценка пути/ускорения `Obd2DriveMetricsTracker` остаётся только экранной метрикой и не меняет позицию/риск. PID 0C, 04 и 11 участвуют в диагностическом `Obd2GearRatioLearner` (RPM/скорость с временной сверкой, нагрузка/дроссель как фильтр ровного движения). PID 0B, 05 и 33 пока не имеют внутренних потребителей. На экране OBD для PID 0C/0D возраст считается по монотонной середине запроса; для остальных полей — приблизительно по времени цикла опроса, поскольку ЭБУ не предоставляет отдельную временную метку.

Для резервной геолокации используется только свежая скорость PID 0D. В режимах «Авто» и «GPS» подключённый OBD-II с актуальной скоростью позволяет **карте** кратковременно продолжить последнюю GPS-оценку максимум на 30 секунд — только если у фикса есть курс, заявленная GPS-точность не хуже 100 метров, а значение скорости не старше 5 секунд; расчётное перемещение ограничено 300 метрами, а оценка погрешности растёт со временем и расстоянием. Если условия не выполнены, карта возвращается к обычному GPS-фиксу либо прекращает показывать его как свежий, а не угадывает направление. Когда foreground-монитор запущен, он также может передавать этот ограниченный прогноз через фиктивный GPS-провайдер, **только если пользователь отдельно включил фиктивную геолокацию**, последний GPS-фикс принят GNSS-фильтром как NORMAL, а координата вне зон риска. Прогноз не подаётся обратно на вход фильтра; тревога, устаревание датчиков, превышение лимита расстояния или смена режима останавливает и очищает его. В режиме «Только радио» единственным источником координат остаётся локальная радиобаза, а свежая скорость может учащать её сканирование в движении. Одна скорость сама по себе не определяет координаты. Последняя скорость кратковременно передаётся между приложением и foreground-сервисом через preference с меткой времени и считается пригодной только 5 секунд; это не история поездок, при отключении она очищается. Поддерживаются Bluetooth Classic RFCOMM/SPP и частично BLE GATT с типовыми парами характеристик записи/уведомлений (включая Nordic UART и распространённые схемы FFE0/FFF0). Некоторые проприетарные клоны и нестандартные GATT-схемы могут не работать; Wi-Fi TCP поддерживается с вручную введённым приватным IPv4-адресом и портом; сначала нужно подключиться к точке доступа адаптера в Android. Clear GPS привязывает только свой TCP-сокет к Wi-Fi-подсети целевого адреса и не переключает сеть автоматически; интернет на точке доступа может быть недоступен. USB пока не поддерживается. На время подключения приложение оценивает путь по свежим отсчётам скорости и показывает сглаженное продольное ускорение. Это не одометр и не история поездки; неизвестные интервалы не заполняются догадками, показатели не влияют на риск спуфинга.

При состоянии TrustEngine `NORMAL` приложение также наблюдает повторяющиеся отношения оборотов к скорости по временно согласованным ответам PID 0C и 0D. Это диагностическое обучение только на время текущего соединения: диапазоны не записываются в профиль автомобиля, не влияют на риск спуфинга и не объявляются реальными номерами передач, поскольку неизвестны окружность шин и главная пара. Используются только пары, прошедшие проверку доверенной GNSS↔OBD-скорости; медленные, устаревшие, разнесённые по времени или высоконагруженные измерения пропускаются.

## Приватность и сетевые запросы

- **Единый сетевой шлюз.** `NetworkGate` проверяет HTTPS, точный хост/путь, HTTP-метод и отдельное согласие; MapLibre и обновление каталога аэропортов проходят через тот же контроль. Для аэропортов разрешён только точный `GET https://davidmegginson.github.io/ourairports-data/airports.csv` при отдельном переключателе согласия. Запросы и блокировки можно увидеть в диагностике, но URL/query/body, API-ключи и радиоидентификаторы в неё не записываются. `network_security_config.xml` запрещает cleartext на уровне Android.

- **BeaconDB — read-only геолокация с отдельным согласием.** Запросы выключены по умолчанию. При включении на `https://api.beacondb.net/v1/geolocate` передаются только текущие поддерживаемые Wi-Fi BSSID/RSSI, допустимые public BLE MAC/RSSI и GSM/WCDMA/LTE Cell ID/RSSI; сервер также видит IP устройства. SSID, Bluetooth-имена/содержимое рекламы, GPS-координаты, история сканирований и накопленные наблюдения не отправляются. API вклада `/v2/geosubmit` не вызывается и заблокирован сетевой политикой. BeaconDB требует POST для read-only geolocate; это единственное узкое исключение из GET-only правил, и оно действует только после отдельного согласия.
- **Краткоживущий кэш BeaconDB.** Успешная геооценка остаётся только в ограниченном in-memory cache до 2 минут; идентификаторы, ответ и координаты не записываются в SQLite и не становятся обучающими fingerprints. Попадание кэша не вызывает сетевой запрос.
- **OpenCellID — отдельный read-only источник.** Личный API-ключ хранится зашифрованным через Android Keystore. При включённых разрешении источника и сетевом переключателе выполняется только HTTPS `GET /cell/get` для текущих поддерживаемых GSM/UMTS/LTE/NR ячеек; передаются их идентификаторы и API-ключ, а сервер также видит IP устройства. Wi-Fi/BSSID, RSSI, BLE, GPS-координаты и история наблюдений не передаются. Автообновление при активном мониторинге ограничено тремя ячейками на пакет, паузой 15 минут и локальным бюджетом 100 попыток за UTC-день; найденные/не найденные ответы хранятся отдельно 30/7 дней. Endpoint добавления измерений не используется.
- **Нет автоматической выгрузки личных измерений.** Сканирования, подписи, координаты, зоны и история хранятся в приватных SQLite/preferences на устройстве. Отдельно разрешённый GET каталога аэропортов скачивает только публичный файл справочника; сервер видит IP устройства, но не получает координаты телефона или радиоданные.
- **Отмена удаления истории источника.** При удалении дня источника или сегмента «дата → тип радио» появляется Snackbar с действием «Отменить», которое транзакционно восстанавливает удалённые строки. Снимок хранится во внутренней SQLite, действует до двух минут и очищается при закрытии Snackbar или начале другой операции изменения базы.
- **Локальные радиоданные.** Полные записи, RSSI-история, SSID, координаты устройства, пользовательские зоны, replay и резервные копии остаются на устройстве и не выгружаются. Только текущий минимальный набор идентификаторов/уровней сигнала, необходимый для явно разрешённого BeaconDB lookup, и только идентификаторы ячеек для OpenCellID lookup могут уйти в эти сервисы; выключение соответствующего переключателя прекращает новые обращения. Bluetooth-имена и содержимое BLE-рекламы не сохраняются и не отправляются.
- **Карта по умолчанию всё ещё онлайн.** MapLibre загружает стили, шрифты и тайлы HTTPS GET с `tiles.openfreemap.org`; сервер видит IP устройства и запрашиваемые участки карты. Радиоидентификаторы и GPS-фикс к картографическим запросам не прикрепляются. В офлайн-режиме сетевые запросы карты блокируются.
- **Ограничения Android остаются.** Система может ограничивать частоту Wi-Fi-сканирования, скрывать часть информации о сотах и использовать рандомизированные Bluetooth-адреса. Clear GPS ограничивает повторный запрос Wi-Fi-скана примерно одним разом в 30 секунд, даже если mock-fix выставлен на 1 секунду: это снижает риск системного троттлинга. При пропуске одного радиосканирования последнее подтверждённое mock-положение можно удерживать только ограниченное время с растущей погрешностью; старые кэшированные данные не продлевают таймер бесконечно. На некоторых версиях/устройствах выключение глобальной геолокации блокирует и Wi-Fi-сканирование.
- **«Только радио» — режим самого приложения.** Обычное Android-приложение не может принудительно выключить GNSS-модуль для всей системы без системных привилегий. Clear GPS может перестать запрашивать GPS-провайдер; передача координат другим приложениям дополнительно требует выбора Clear GPS как приложения фиктивной геолокации в настройках разработчика. Некоторые приложения распознают или игнорируют фиктивные координаты.
- Проект экспериментальный и не гарантирует точность навигации или обнаружение всех вариантов GNSS-спуфинга.

## Сборка на Windows

Запусти **build-apk.bat** из корня репозитория. Сборщик проверяет Java, Android SDK и Gradle; при необходимости он предлагает установить недостающие инструменты после подтверждения. Где доступно, скачиваемые архивы проверяются по хешам.

После успешной сборки APK будет в **dist/ClearGPS-debug.apk**. Также его можно получить как артефакт в [GitHub Actions](https://github.com/MAKAKAIglitch/clear-gps/actions).

## Сборка на Linux и macOS

Требуется совместимый JDK **17–24** (в CI используется JDK 17) и Android SDK с **Platform 36** и совместимыми Build-Tools. Укажи путь к SDK в `ANDROID_SDK_ROOT` или `ANDROID_HOME`, если он не определяется автоматически.

Из корня репозитория выполни:

```bash
./gradlew --no-daemon --stacktrace :core-detect:test testDebugUnitTest assembleDebug
```

Wrapper скачивает Gradle 8.14.6 при первом запуске и проверяет SHA-256 дистрибутива по значению из `gradle/wrapper/gradle-wrapper.properties`. Для первого запуска требуется доступ к `services.gradle.org`. Готовый debug APK будет в `app/build/outputs/apk/debug/app-debug.apk`.

## Карты и атрибуция

По умолчанию используются стили [OpenFreeMap](https://openfreemap.org/) на основе OpenMapTiles / OpenStreetMap. Атрибуция показывается в приложении. Публичные стили OpenFreeMap удобны, но требуют интернет; перед реализацией офлайн-загрузки или более крупного кэширования изучи актуальные [условия сервиса](https://openfreemap.org/tos/). Карты не включены в APK.

## Статус разработки

Это исследовательский проект. Сборка и unit-тесты автоматизированы, но полный сценарий сканирования/записи/редактирования/радионавигации ещё нужно проверять на реальных телефонах Android разных производителей. Указанный радиус точности локальной оценки — эвристика, а не измеренная гарантия.
